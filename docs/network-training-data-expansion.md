# План расширения обучающих данных сетевого классификатора

Составлен 22.11.2026 после аудита признаков v10 и абляции портов
(`docs/network-model-release-gate.md`, разделы от 22.11.2026). Статус:
черновик; ничего из перечисленного ниже не скачивалось и не открывалось.

## Зачем

На CTU-13 модель учится различать ОС заражённых VM (Windows XP, исходные
порты 1024–5000), а не поведение ботнета. Train содержит 3 семейства
(Neris, Rbot, Sogou), почти не содержит ICMP/UDP-флуда и не содержит
современной Windows и Linux/IoT-хостов. Дальнейшая подстройка на CTU-13
dev не исправит перенос; нужны новые реальные захваты.

## Правила приёма источника (из AGENTS.md и release gate)

1. Только реальные захваты; метки — опубликованные владельцем набора
   (publisher labels). Записываются источник, URL, лицензия, SHA-256 и
   контрольная сумма издателя, правило сопоставления меток.
   Background/unknown не считаются benign.
2. **Роль назначается до чтения меток**: `train`, `dev` или
   `reserved_independent_test`. Резерв не открывается до регистрации
   замороженного кандидата и используется один раз.
3. **Предпочтителен PCAP + собственный парсер**
   (`integrityguard.network_packet_flows.aggregate_capture`): тогда
   признаки совпадают с живыми потоками из Pktmon. Готовые CSV
   (CICFlowMeter, Argus, NetFlow) допустимы только с явным адаптером и
   записью расхождений семантики (таймауты, направление, счётчики).
4. Для каждого источника фиксируются ОС атакующих и жертв, семейства и типы
   атак. Признаки, повторяющие свойства стенда (величины портов, TTL, адреса),
   в модель не входят.
5. Дедупликация точных дубликатов и проверка утечек по хостам и времени до
   разбиения; split — по целым захватам/сценариям/дням.
6. Стендовые (testbed) наборы — это реальные пакеты, но фоновый трафик
   там генерируется агентами. Они годятся для train/dev разнообразия атак,
   но **не** для заявлений о FPR на целевой сети.

## Предлагаемый порядок

1. **Закрыть пробел по ICMP/UDP-флуду.** Скачать несколько PCAP CICIoT2023:
   Benign, DDoS-ICMP_Flood, DDoS-UDP_Flood, DDoS-SYN_Flood, Mirai.
   Прогнать их через `aggregate_capture`, проверить метки на уровне файлов,
   добавить в train.
2. **Добавить другие ОС.** Взять PCAP CIC-IDS-2017 Monday (benign) и
   Friday (бот ARES, DDoS, PortScan) с переразметкой Engelen. Sport-артефакт
   проверять заново: исходные порты Windows 7+ лежат в 49152–65535.
3. **Зарезервировать нетронутый независимый тест.** Подходит UNSW-NB15 или
   один целый сценарий CICIoT2023 с отдельными устройствами. Роль закрепить
   до чтения меток.
4. **Повторить аудит признаков** (`tools/audit_feature_semantics_v10.py`
   нужно обобщить на новые адаптеры) по всем train/dev-источникам, затем
   зарегистрировать новый кандидат.

Этот путь не закрывает целевой gate. Для заявлений о вашей сети по-прежнему
нужны локальные захваты с независимо подтверждёнными метками.

## Инструмент потоковой загрузки (22.11.2026)

`tools/stream_ingest.py` (логика — `integrityguard/stream_ingest.py`) читает
pcap/pcapng последовательно из локального файла или по HTTP(S). Поддерживаются
`.gz` и отдельный член ZIP-архива: член читается через HTTP Range, остальные
члены архива не передаются. Сырые пакеты, payload и IP на диск не пишутся.
Сохраняются только:

- `<source_id>.npz`: признаки v10 (46), метки 0/1, номер окна и `first_seen`
  для разбиения по времени;
- `<source_id>.manifest.json`: источник, SHA-256 и MD5 байтов захвата, проверки
  контрольных сумм, правило меток (полностью и его SHA-256), SHA-256 парсера и
  инструмента, счётчики (пакеты, окна, потоки, исключённые), роль и метаданные
  (ОС, семейство, тип атаки).

Семантика совпадает с живым сенсором. Временная шкала режется на окна по 10 с,
как `capture_header_segment`. Каждое окно агрегируется той же функцией
`network_packet_flows.aggregate_packets`, которую теперь вызывает и
`aggregate_capture`; это чистый рефакторинг без изменения поведения.
Сохраняются только потоки с `complete=True`, то есть те, которые оценивает
runtime.

Ограничения и проверки:

- роли только `train`/`dev`; `reserved_independent_test` отклоняется;
- шард не пишется при ошибке разбора, несовпадении контрольной суммы или пустом
  результате; существующие шарды не перезаписываются;
- метки ставит явное правило издателя (first-match по IP/CIDR, протоколу,
  времени; по умолчанию `exclude`). IP служат только для разметки и не являются
  признаками.

`train_v9.py --ctu-extra-train-shards <manifest>...` добавляет шарды только в
train. Каждый шард идёт отдельной группой для capture weighting; SHA-256
манифестов входят в fingerprint запуска и в provenance отчёта.

Проверено:

- 8 детерминированных тестов кода (`tests/test_stream_ingest.py`) на
  байтовых фикстурах; это не данные для модели;
- 65 сетевых тестов проекта;
- на реальном `ctu-42-botnet-only.pcap` потоковый путь с одним окном дал тот же
  SHA-256 (`b89cd593…`), 323 154 пакета и 14 521 поток с идентичными признаками
  v10 и флагами завершённости, что и `aggregate_capture`;
- с окнами 10 с: 1 705 окон, 39 443 потока, из них 11 488 завершённых.

Новые источники ещё не загружались. Рабочий EXE не пересобирался:
рефакторинг парсера попадёт в приложение только со следующей сборкой.

## CICIoT2023: подготовка (22.11.2026)

Источник разметки — статья издателя (Neto et al., Sensors 2023,
doi:10.3390/s23135941, полный текст PMC10346235). Ключевые факты:

- атаки выполняют 7 Raspberry Pi (Linux), жертвы — IoT-устройства; в Table 1
  указаны MAC трёх Pi 4 (`DC:A6:32:C9:E6:F4`, `…E4:C6`, `…E5:02`), Pi среди
  жертв нет;
- benign-захват — 16 ч без атак, простой и действия людей;
- **издатель метит весь захват атаки этой атакой**, без разметки по потокам,
  поэтому фоновый трафик других устройств внутри файла атаки помечен как атака;
- инструменты: `udp-flood` (UDP Flood), `hping3` (SYN, ICMP и другие флуды);
  исходный трафик ~548 ГБ.

Правила `tools/label_rules/ciciot2023-*.json` уточняют метку издателя до
уровня потоков. Атакой считается только поток, у которого Ethernet-источник
инициатора имеет OUI Raspberry Pi 4 `DC:A6:32` и протокол соответствует типу
флуда. Остальное исключается, а не считается benign. Для этого
`stream_ingest` получил ключ правила `mac_src`. MAC используются только для
разметки и не сохраняются. Перед обучением нужно проверить на данных, что
источников с этим OUI не больше 7.

**Ограничение приложения, найденное при подготовке.** Runtime оценивает только
`complete`-потоки: TCP с SYN и FIN/RST и UDP после 1 с тишины. ICMP-потоки
никогда не бывают завершёнными, поэтому ICMP-флуд приложение сейчас не
оценивает вообще. SYN-флуд без RST от жертвы тоже не оценивается. Обучающие
шарды повторяют это поведение. Чтобы детектор видел такие атаки, нужно
отдельное решение о правиле завершения для ICMP и полуоткрытых TCP, иначе
данные ICMP-флуда не дадут ни одной обучающей строки.

**Доступ.** Скачивание закрыто формой CIC (имя, email, организация, должность,
страна). Её заполняет пользователь; потом инструмент работает по выданной
ссылке.

### Тайм-аут завершения ICMP и полуоткрытого TCP (22.11.2026)

`network_packet_flows.aggregate_packets` теперь завершает ICMP после 1 секунды
бездействия; полуоткрытый TCP завершается по такому же тайм-ауту только если
инициатор отправил SYN и больше ни одного TCP-пакета. Завершённые TCP с FIN/RST
сохраняют прежнее правило. UDP без изменений: 1 секунда тишины. При отсутствии
доверенного конца захвата потоки с тайм-аутом остаются незавершёнными. Причина
завершения показывается в подсказке графика; манифест обучающего шарда фиксирует
правила.

Проверка кода: полный набор `pytest` — 131 passed, 9 skipped. На реальном
`ctu-42-botnet-only.pcap` (323154 пакета, 14521 поток) с явно заданным концом
захвата разобраны 11686 TCP, 2758 UDP и 76 ICMP потоков. Завершены 9654 TCP
только-SYN по тайм-ауту, 2022 TCP через FIN/RST, все 2758 UDP и 76 ICMP;
11 прочих потоков остались незавершёнными. Это проверка работы парсера, не
оценка качества модели.

EXE приложения не пересобирался по просьбе пользователя. Ярлык
`IntegrityGuard.lnk` запускает существующий `dist/IntegrityGuard/IntegrityGuard.exe`;
обновление исходников тайм-аутов в этом EXE пока не действует.

## Тайм-аут завершения для ICMP и полуоткрытого TCP (23.11.2026)

По решению пользователя в `network_packet_flows.aggregate_packets` добавлены два
правила завершения, оба с тем же проверенным тайм-аутом бездействия 1 с до
конца сегмента, что и у UDP:

- `icmp_idle_timeout_1s` — ICMP-поток завершён, если его последний пакет был
  не позже чем за 1 с до конца сегмента;
- `tcp_half_open_idle_1s` — TCP-поток, где инициатор отправил **только SYN**
  (ровно один пакет), FIN/RST нет, и поток бездействует 1 с. Это SYN-флуд и
  неотвеченные попытки соединения. Установленные соединения без FIN/RST
  (инициатор отправил больше одного пакета) по-прежнему остаются незавершёнными.

Без отметки времени конца сегмента (офлайн `aggregate_capture(path)`) такие
потоки, как и UDP, остаются незавершёнными. Подсказка графика потоков в GUI
показывает новые причины завершения. Прочие протоколы (`other`) не меняются.

Влияние на реальном `ctu-42-botnet-only.pcap` (окна по 10 с, 39 443 потока):
завершённых стало **28 082** вместо 11 488. Прирост дали 16 265 полуоткрытых TCP
(попытки соединений ботнета; издатель метит их `TCP-Attempt`) и 329 ICMP;
незавершёнными остались 9 035 TCP, 2 262 UDP, 63 ICMP и 1 other. Потоковый путь
по-прежнему побайтно совпадает с файловым.

Последствия:
- runtime теперь оценивает больше потоков, в том числе ICMP и неотвеченные SYN.
  Текущий v3-кандидат на таких потоках не проверялся, его оценки остаются только
  рекомендацией, блокировка не включена;
- шарды, собранные до этого изменения, нельзя смешивать с новыми: у манифеста
  поменялись `parser_sha256` и `completion_rules`;
- 131 тест проекта проходит (новые тесты: ICMP/полуоткрытый TCP закрываются по
  тайм-ауту, установленный TCP без FIN — нет, без времени конца сегмента — нет).
