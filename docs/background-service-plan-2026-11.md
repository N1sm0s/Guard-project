# План этапа P2 — фоновая работа (с 23.11.2026)

Основа — [development-roadmap.md](development-roadmap.md), строка P2. Критерий
приёмки из карты: служба без входа пользователя, минимальные привилегии,
устойчивость очереди при аварии, проверяемое восстановление, обновление с
откатом, длительный прогон с измерением ресурсов.

## Что уже есть в коде (проверено 23.11.2026)

| Требование | Что есть | Чего не хватает |
|---|---|---|
| Устойчивость очереди при аварии | `intake.py`: ledger `intake_pending` с fingerprint, повторами с экспоненциальной задержкой и карантином повреждённых записей; `recover_archived` восстанавливает прерванный перенос | Проверка на реальном сбое процесса во время переноса (сейчас тесты имитируют исключения) |
| Атомарная запись журнала | `journal.py`: BEGIN IMMEDIATE, fsync, идемпотентность по `event_id`, восстановление после сбоя после записи | Проверка при потере питания (только имитация) |
| Монитор с контрольной точкой | `test_monitor.py`: идемпотентность после перезапуска, ограниченные повторы | Контрольная точка под нагрузкой |
| Служба без входа пользователя | **нет** — `schtasks` и сервисная обвязка в коде отсутствуют | Всё: установка службы, учётная запись, автозапуск |
| Минимальные привилегии | **нет** — приложение работает от пользователя; pktmon требует администратора | Разделение: служба с минимумом прав и отдельный привилегированный сбор |
| Обновление с откатом | Резервные копии `dist\IntegrityGuard-backup-*` делаются вручную | Автоматизированная процедура обновления и отката с проверкой |
| Длительный прогон и ресурсы | Есть разовые замеры P95 инференса (не целевые) | Нагрузочный прогон с замерами CPU, памяти, очереди |

## Шаги (порядок выполнения)

### P2.1. Крэш-тесты очереди и журнала на реальном процессе — **[я]** — сделано 23.11.2026
Добавлено `tests/test_crash_recovery_p2.py`: 2 теста на дочерних процессах (сбой
после записи журнала до переноса; повторные сбои при переносе). Проверяют один
перенос, один анализ и одну запись журнала по `event_id`. Сбой при переносе уже
покрыт в `test_intake.py`. Потеря питания не моделируется: это требует стенда.
- Запускать дочерний процесс, который обрабатывает очередь, и принудительно
  завершать его в середине переноса и в середине записи журнала (`os._exit`
  через точку внедрения).
- Критерий: после перезапуска каждая запись либо перенесена ровно один раз,
  либо остаётся в очереди; дублей журнала нет; карантин срабатывает на порче.
- Без изменения рабочего EXE; только тесты.

### P2.2. Нагрузочный прогон очереди — **[я]**
- Синтетические *пакеты-файлы* здесь допустимы: они проверяют очередь, а не
  качество модели. Это должно быть явно указано в отчёте.
- Замеры: число записей в секунду, пиковая память, время восстановления после
  сбоя на 1 000 записях. Результаты — в `docs/` с SHA-256 окружения.

### P2.3. Процедура обновления с откатом — **[я]**
- Скрипт: сохранить текущую сборку в резерв с хешами, поставить новую,
  проверить `--selftest-gui` и путь процесса, при провале вернуть резерв.
- Тест на копии каталога (без установки в систему).
- Требует вашего решения о том, где хранить резервы (сейчас в `dist/`).

### P2.4. Служба без входа пользователя — **[вы решаете]**
- Установка службы Windows меняет систему и требует прав администратора.
  Без вашего отдельного подтверждения я её не устанавливаю.
- Варианты: Windows-служба через обёртку (например, NSSM или pywin32) или
  задача планировщика при запуске системы. Выбор и учётная запись — за вами.
- До решения этот шаг остаётся открытым, а P2.1–P2.3 выполняются без него.

### P2.5. Разделение привилегий — **[вы решаете]**
- Pktmon требует администратора; основная логика должна работать без него.
- Предлагаемый вариант: привилегированная часть только собирает счётчики и
  пишет в очередь; анализ и интерфейс работают от обычного пользователя.
- Требует архитектурного решения и затрагивает `pktmon_capture.py`.

## Критерии завершения этапа

- P2.1 и P2.2 выполнены, результаты записаны.
- P2.3 проверен на копии каталога, процедура описана.
- P2.4 и P2.5 либо реализованы по вашему решению, либо явно записаны как
  открытые пункты с причиной.

## Что не делаем в этом этапе

- Не меняем алгоритмы классификатора и порог выпуска.
- Не включаем блокировку по результатам модели.
- Не устанавливаем службы и не меняем учётные записи без вашего подтверждения.
