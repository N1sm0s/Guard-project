# Сетевой классификатор: release gate

Полоса «Готовность к релизу сетевой модели» в приложении показывает долю закрытых пунктов из десяти равновесных технических этапов. Это индикатор процесса допуска, а не точность, вероятность обнаружения или «процент знаний» нейросети.

## Действующее правило выбора порога

Новый release-предел действует проспективно с 20.11.2026. С 20.11.2026 предел изменён с 0,1% на 0,25%; это правило применяется только к новым регистрациям и не меняет уже зарегистрированные оценки. Их evaluator, порог и выводы сохраняются; ранее использованные тестовые данные нельзя задним числом засчитать как независимое подтверждение нового gate.

Для development-подбора CLI по умолчанию использует верхнюю 95% Wilson CI FPR ≤0,25% отдельно на каждом whole-capture dev-наборе (`--ctu-dev-fpr-ci-ceiling 0.0025`). Это исследовательское ограничение нужно для сравнения кандидатов и не является релизным допуском.

Проспективный release gate: на каждом новом независимом тест-захвате верхняя двусторонняя 95% Wilson CI FPR должна быть ≤0,25%, нижняя 95% CI полноты — ≥80%, а объём выборки должен удовлетворять требованиям этапов ниже. Это компромисс для квалификации кандидата при ограниченном объёме реальной разметки, а не утверждение, что 0,25% ложных срабатываний приемлемы для любой сети. Верхняя граница соответствует до 2,5 ложных срабатываний на 1 000 benign-потоков; абсолютный объём и стоимость таких срабатываний нужно оценить на целевой нагрузке. При нуле FP требуется минимум 1 533 benign-потока на захват; при FP объём определяется фактическим Wilson-интервалом и может быть больше. Изменение порога само по себе не включает блокировку: для неё остаются обязательными остальные этапы gate и проверенный операционный предел ложных блокировок. Исторические результаты сохраняют пороги, реально применённые в соответствующих запусках.

При текущем dev-пределе это требование действует и при выборе эпохи checkpoint: на каждой эпохе выбирается общий порог, который удовлетворяет dev-FPR CI на каждом захвате; checkpoint ранжируется по максимальной минимальной per-capture нижней CI полноты, затем по средней полноте и NLL. Это development-only процедура, не просмотр independent test.

В разделе обучения интерфейс показывает реальные train loss и development NLL по левой шкале, а minimum development recall CI-L — по правой; статус выбранной схемы включает dev threshold и применённый dev FPR CI ceiling. График не меняет release gate и не трактуется как процент готовности модели.

## Этапы допуска

1. Проверены происхождение обучающего корпуса, checkpoint и manifest.
2. Есть обученный checkpoint на реальных потоках с опубликованными метками.
3. Train, validation и независимый test разделены по целым захватам.
4. Per-flow inference подключён к Pktmon-сенсору.
5. На каждом новом независимом source-test захвате нижняя 95% Wilson CI полноты атак не ниже 80%, верхняя 95% CI FPR не выше 0,25% при пороге, зафиксированном на validation.
6. Выполнена отдельная оценка на целевой сети с первичными источниками меток; до расчёта результата SHA-256 захвата и манифест меток зафиксированы, а checkpoint в отчёте совпадает с оцениваемой моделью.
7. Target-test содержит минимум 100 атак и достаточно нормальных потоков для верхней 95% CI FPR не выше 0,25%. При 0 ложных срабатываниях двухсторонний 95% Wilson-интервал требует не менее 1 533 нормальных потоков. При наличии FP требуемый объём выше и определяется по вычисленному интервалу.
8. Сенсор измеряет потери и неполноту захвата; полнота данных отчётно известна.
9. Измерена задержка inference на целевой нагрузке и подтверждена достаточная производительность.
10. Сквозное действие проверено: аудит вердикта, безопасная обработка неизвестного потока и откат модели/правила.

Потоки без первичного ground truth, модельные score, частота соединений и threat-intel совпадения не дают метку. Их можно анализировать и показывать как рекомендации, но нельзя включать в supervised-метрики или считать подтверждённой нормой.

**Определение gate 8:** измеряется потеря данных самого сенсора/захвата, а не сетевые потери, вызванные Windows, драйвером или удалённым узлом. Pktmon показывает высокоуровневые счётчики по компонентам стека; один пакет может отображаться на нескольких компонентах. Поэтому суммы per-component счётчиков нельзя использовать как число уникальных пакетов или как packet-drop rate сенсора. До допуска нужно подтвердить документированный счётчик потерянных ETL-событий либо валидированно сопоставить уникальные packet groups на выбранной NIC-точке с записями, разобранными приложением. Один флаг `drop_counters_available` или SHA-256 снимка счётчиков этого не доказывает.

## Операционная телеметрия

Приложение фиксирует длительность прямого inference на каждом успешном Pktmon-сегменте в `data/online/network_runtime_metrics.sqlite`. Записи append-only и связаны SHA-256 цепочкой; перед отображением проверяется целостность всей цепочки. В интерфейсе показывается наблюдаемый P95 и число сегментов. Это локальный runtime показатель, не контролируемый target-load тест; он сам по себе не закрывает gate 9.

В конце Pktmon-сегмента приложение также пытается получить `pktmon counters --json`. Сохраняется только SHA-256 снимка и признак его доступности; сами сведения о сетевых компонентах в БД не записываются. Снимок пока не преобразуется в подтверждённый packet-drop rate: счётчики по компонентам могут учитывать прохождение одного пакета через несколько уровней сетевого стека. Gate 8 остаётся открытым до проверки корректного знаменателя и сопоставления с реальным сегментом.

## Сбор целевых потоков для будущей разметки

Исправление пробела в сборе данных внесено в приложение: Pktmon преобразует краткий захват в потоковые метрики, после чего удаляет временные ETL/PCAPNG. Обновлённая сборка установлена в `dist/IntegrityGuard`; packaged GUI self-test завершился с кодом 0, и окно из штатного EXE отвечает. После успешного Pktmon захвата приложение сохраняет SHA-256 PCAPNG и payload-free записи потоков в `data/online/network_runtime_metrics.sqlite`, привязанные к хешу записи сегмента. Потоковый журнал имеет отдельную append-only hash chain; `runtime_summary()` проверяет его целостность. В каждой записи принудительно остаётся `label_status=unknown`; прогнозы модели не пишутся в этот журнал и не превращаются в обучающие метки. Содержимое пакетов не хранится; для корреляции с первичными событиями сохраняются IP/порты, время, счётчики, флаги и рассчитанные признаки. Живой Pktmon сегмент с новой версией журнала ещё не зарегистрирован: приложение перезапущено без elevation, а Pktmon требует администратора. Функция не создаёт ground truth и не закрывает пункты 6–8.

Чтобы получить пригодный target-test, нужно: (1) накопить интервалы без генерации тестового трафика; (2) связать потоки с независимыми первичными источниками — например, подтверждёнными расследованиями/EDR/IDS для инцидентов и инвентарём активов плюс проверенными журналами сервисов для benign; (3) оставить несопоставленные и спорные события unknown; (4) сформировать manifest с источниками, временным окном, capture hash, mapping rules и явно размеченными строками; (5) отложить последующий интервал как независимый test, закрепить его вместе с checkpoint до расчёта метрик. По текущему проспективному пределу при нуле FP требуется минимум 1 533 подтверждённых benign flows для верхней двусторонней 95% Wilson границы FPR ≤0,25%; также нужно ≥100 подтверждённых атак и нижняя CI полноты ≥80%. Если реальные инциденты не появятся, решение — увеличить период сбора или честно оставить gate открытым, а не назначать метки по модели, фону или неполным TI совпадениям.

В проверенной текущей пользовательской сессии Pktmon ответил `Access denied`, поэтому свежие сенсорные измерения ещё не созданы. Нельзя выводить измеренный P95 или packet-drop rate из отсутствующих сегментов.

Подробные исходные метрики и происхождение: `models/network_flow_v3_candidate_metrics.json` и `models/network_flow_v3_candidate_manifest.json`.

### Порядок закрытия оставшихся пробелов

1. **Сначала исправить и доказать сбор:** прежний GUI запускал 10-секундный захват раз в 60 секунд (около 17% времени без учёта накладных расходов). В исходнике интервал теперь увеличен до 30-секундных сегментов с повторным запуском каждые 30 секунд; фактическую долю покрытия ещё нужно измерить по реальным таймстампам и счётчикам. Агрегатор всё ещё финализирует TCP только при SYN и FIN/RST внутри одного файла, а UDP всегда помечает незавершённым. Поэтому нужен непрерывный/непрерывно ротируемый захват и единый stateful flow tracker с документированными idle-timeout и неполнотой наблюдения между сегментами; нельзя выдавать обрезанный сегмент за полный Zeek-подобный поток. Предварительная запись `capture_started` удалена: статус теперь записывается по фактическому результату вызова Pktmon. Затем в повышенной пользовательской сессии получить сегменты с `packets_seen > 0`, подтверждёнными полными потоками, валидной capture-chain и per-flow inference для одного SHA checkpoint. Если потоков всё ещё нет, сбор корпуса не начинать.
2. **Разделить журнал наблюдений и разметку:** сохранять все потоки как `unknown`. Привязывать метку атаки только к первичному incident/EDR/IDS-событию с подтверждённой временной и сетевой корреляцией; benign — только в ограниченных окнах подтверждённого штатного актива/сервиса и сверенных журналов. Несопоставленные и спорные потоки оставить unknown. GUI-решение, модельный score и простое отсутствие алерта не являются ground truth.
3. **Заранее зарегистрировать target test:** выбрать будущий временной интервал целевой сети, записать SHA-256 захвата, label manifest, правила корреляции, extractor/evaluator и candidate SHA до запуска оценки. Ни порог, ни признаки, ни состав модели после раскрытия результата не менять; использованный интервал станет development data только для следующей версии.
4. **Собрать достаточную поддержку:** нужно не менее 100 подтверждённых атак с нижней 95% Wilson CI recall ≥80% и столько подтверждённых benign, сколько требуется для верхней 95% Wilson CI FPR ≤0,25%. При нуле FP это минимум 1 533 benign; при FP объём увеличивается. Если реальные инциденты редки, продлевать наблюдение или получать подходящие независимые реальные инцидентные captures с первичными метками, не размечать фон как benign.
5. **Повторить gate после модели:** checkpoint и порог выбираются только на train/validation captures; каждый ранее оценённый capture остаётся consumed для этой пары. После target-test открыть оценки только после фиксации manifest. Отдельно довести измерение потерь сенсора, P95 на целевой нагрузке и аудит/откат действия. До прохождения всех пунктов автоматическую блокировку не включать.

Для проектирования следующего сенсорного шага сверены первичные спецификации: Microsoft Pktmon `multi-file` создаёт последовательно нумеруемые ETL-файлы при достижении лимита файла, а `real-time` выводит события на экран без файла; поэтому реализация должна явно управлять ротацией, обработкой уже закрытых сегментов и объёмом хранилища ([Pktmon start](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/pktmon-start)). Для сопоставимости с Zeek-derived train данные Zeek задают стандартный inactivity timeout 5 минут для TCP и 1 минуту для UDP; это ориентир для семантики завершения flow, который нужно закрепить в версии extractor-а и проверить на целевых данных ([Zeek connection timeouts](https://docs.zeek.org/en/current/scripts/base/init-bare.zeek.html)). Документация подтверждает доступные механизмы, но не доказывает, что нынешний IntegrityGuard уже реализует непрерывный захват или полные flow.

### Поиск независимого набора: ICS-NAD (20.11.2026)

Проверена публикация Scientific Data 2026 и описание исходного набора ICS-NAD (DOI `10.57760/sciencedb.25938`). Публикация описывает два расписанных паттерна атаки (1 минута штатного трафика + 4 минуты атаки; либо повторные 30-секундные всплески) и набор объёмом 245.96 GB / 272 файлов.

Вывод: **не загружать 245.96 GB и не включать этот источник в release train/test**. Он может стать отдельным OT стресс-тестом только после регистрации capture-level split, анализа label-rule leakage и собственного extractor-а из PCAP. Первоисточники: [публикация и метод разметки](https://pmc.ncbi.nlm.nih.gov/articles/PMC12996622/), [официальный репозиторий Science Data Bank](https://doi.org/10.57760/sciencedb.25938).
