# IntegrityGuard — нейросетевой контроль целостности пакетно-нейросетевых программ

Программное средство по теме «Разработка модели системы защиты информации, основанной на
проблемно-ориентированной конструкции нейронных сетей, в интересах выявления угроз нарушения
целостности пакетно-нейросетевых программ (ПНП)».

## Запуск

1. Один раз запустите `install.bat` — он создаёт окружение Python, устанавливает библиотеки,
   собирает portable-приложение и создаёт ярлык на рабочем столе (и в каталоге проекта), если
   ярлыков ещё нет. Для установки нужен Python 3.10+.
2. Запускайте `F:\New\integrityguard\dist\IntegrityGuard\IntegrityGuard.exe` или уже имеющийся ярлык.

### Сборка Windows-дистрибутива

`build_exe.bat` пересобирает onedir-дистрибутив в `dist/IntegrityGuard/`.
`create_shortcut.ps1` при первом запуске создаёт ярлыки (на рабочем столе и в каталоге проекта); при
повторных запусках обновляет путь у уже существующих ярлыков. `install.bat` вызывает этот скрипт
автоматически после сборки.
В отличие от исходного режима, сборка хранит настройки, реестр и журналы в
`%LOCALAPPDATA%/IntegrityGuard/data`, чтобы не записывать их в каталог программы.
PyInstaller устанавливается в `.venv` только для сборки и не добавляется в runtime-зависимости.

## Структура проекта

- `integrityguard/` — код приложения и детектора.
- `assets/`, `models/` — ресурсы интерфейса и основная модель.
- `corpus/`, `data/` — обучающий корпус и локальные данные приложения в режиме разработки.
- `docs/`, `tests/`, `tools/` — методика, проверки, диагностика и оценка внешних пакетов.
- `tools/maintenance/` — разовые скрипты исправления, сохранённые для истории разработки.
- `outputs/` — результаты экспериментов, отчёты и скриншоты тестовых прогонов.
- `build/`, `dist/`, `.venv/` — генерируемые файлы сборки и окружение Python.

`run.bat` запускает исходный код для разработки. Для обычного запуска используйте ярлык на portable EXE.

В окне: «Проверка пакета» → либо кнопка «Показать на примере» (один клик — программа сама создаёт демо-набор,
если его ещё нет, и сама же показывает результат), либо кнопка «Обзор…» и выбор своего каталога (тоже один-два
клика, дальше ничего нажимать не нужно). Обученный детектор уже лежит в `models/`, обучать заново не обязательно.

Страница «Проверка пакета» рассчитана на первый запуск без инструкции: сверху — только поле для своего пакета
и кнопка «Показать на примере» через разделитель «или», больше ничего выбирать не нужно. Как только указан
каталог пакета (кнопкой «Обзор…», выбором демо-пакета или просто вписанным путём), проверка запускается сама,
сразу же, без отдельной кнопки или галочки. Под полем появляется строка статуса («Автопроверка включена: …»),
и дальше проверка повторяется сама при каждом изменении файлов в этом каталоге (интервал опроса — 4 секунды).
Остановить автопроверку можно только одним способом — очистить поле с путём. Указанный путь сохраняется и
восстанавливается при следующем запуске программы (в том числе при автозапуске в трее, см. ниже) — наблюдение
возобновляется само, без повторного выбора. Стадия, строгий режим, выбор конкретного демо-пакета, ручная
кнопка «Проверить» и «Проверить все демо-пакеты» убраны в свёрнутый по умолчанию блок «Дополнительные
параметры» — они нужны не всем и не при первом запуске.

Вкладка «Мониторинг» показывает графики: поток пакетов, поступающих на проверку (по времени и вердиктам),
оценки нарушения, распределение заключений и входящие сетевые пакеты компьютера (нужна библиотека `psutil`,
её ставит `install.bat`).

## Автоматический режим (включён по умолчанию)

- При первом запуске программа сама создаёт демонстрационные пакеты, регистрирует эталон и проверяет весь набор.
  Если файла детектора нет — сама формирует корпус и обучает сеть.
- Папка `data/incoming` — входящие пакеты. Скопируйте туда каталог пакета: он будет проверен без нажатий и
  переложен в `data/processed/allow`, `review` или `block` (карантин). Некорректный каталог уходит в `error`.
- Пакет с новым именем считается доверенным, подписывается ключом реестра и становится эталоном
  (доверие при первом появлении). Контрольный набор берётся из `control.npz` внутри каталога, если он есть.
- Графики, журнал и история обновляются сами. Недостающие небольшие библиотеки доустанавливаются при запуске.
- Отключается галочкой на вкладке «Настройки».

### Работа в фоне (значок в трее) и автозапуск

- Закрытие окна (крестик) не завершает программу — она сворачивается в значок в системном трее и
  продолжает проверять входящие пакеты. Через меню значка (правая кнопка мыши) можно открыть окно снова,
  включить/выключить автоматический режим или выйти из программы по-настоящему.
- На вкладке «Настройки» есть галочка «Запускать автоматически при входе в Windows (в трее, без открытия
  окна)». Она добавляет (или убирает) ключ автозапуска в реестре текущего пользователя
  (`HKCU\...\CurrentVersion\Run`) без установки службы и без прав администратора. При входе в Windows
  программа запускается сразу в трее и начинает проверять входящие пакеты без участия пользователя.
- Ручной запуск в трее (минуя автозагрузку): `IntegrityGuard.exe --tray`.

## Что делает программа

Кандидат (новая версия пакета) сравнивается с доверенным эталоном на трёх уровнях целостности.

| Уровень | Что анализируется | Ветвь сети |
|---|---|---|
| Структурный | граф компонентов: зависимости, модули, модель, слои; версии, хеши, источники, «возможности» кода (сеть, запуск процессов, eval, обфускация…), тайпосквоттинг | графовая нейросеть (GNN) |
| Параметрический | портрет каждого слоя: статистика распределения весов, спектр (сингулярные числа), отклонение от эталонного слоя; архитектура кодировщика выбирается автоматически (MLP/CNN/LSTM/Transformer) | автокодировщик весов (WeightAE) |
| Поведенческий | отклик на контрольные входы и обратная реконструкция триггера (поиск минимального возмущения, переводящего входы в один класс) | классификатор аномалий |

Блок объединения выдаёт класс нарушения; дополнительно — оценки по уровням и указание
подозрительного компонента (зависимость, модуль, слой).

### Классы нарушений (9 классов)

| № | Класс | Описание | Уровень целостности |
|---|---|---|---|
| 0 | `clean` | Нарушений нет (легитимное обновление) | — |
| 1 | `dependency` | Компрометация библиотек и компонентов | структурный |
| 2 | `weights` | Подмена или изменение весов модели | параметрический |
| 3 | `backdoor` | Внедрение триггера (бэкдора) | поведенческий |
| 4 | `poison` | Отравление обучающих данных | поведенческий |
| 5 | `label_flip` | Подмена меток | поведенческий |
| 6 | `adversarial` | Состязательные входы / эвазия модели | поведенческий |
| 7 | `extraction` | Несанкционированное извлечение модели | структурный |
| 8 | `availability` | Нарушение доступности (атака типа DoS) | поведенческий |

## Результаты (синтетический корпус, 500 проектов)

| Метод | F1 (бинарный) | AUC-ROC | Macro-F1 (9 классов) |
|---|---|---|---|
| Гибридный детектор (HybridDetector) | **1,000** | **1,000** | **0,687** |

Это результаты текущего отчёта `models/report.md` на отложенных 81 синтетических проекте. Бинарное разделение
«норма / нарушение» для этого синтетического генератора практически полностью решено (см. `docs/methodology.md`
про риск переобучения на шаблонах генератора — идеальные бинарные показатели на таком корпусе не являются
доказательством качества на реальных инцидентах). Более показательна многоклассовая задача (какой именно это
класс угрозы): macro-F1 0,687. Классы `backdoor`, `poison` и `label_flip` заметно путаются между собой
(все три получаются через дообучение на повреждённых данных и дают похожие портреты весов) — здесь нужна
дальнейшая работа. Обнаружена и исправлена ошибка, из-за которой поведенческая ветвь детектора ранее не
получала никакого сигнала (см. `tools/extract_features.py` и `docs/methodology.md`); после исправления
поведенческий уровень различает классы с AUC 0,857 вместо случайных 0,5.

Полный отчёт: `models/report.md`, числа: `models/metrics.json`, диаграммы: `models/metrics.png`.
Показатель «Fulnes» (написание как в ТЗ) трактован как полнота (Recall).

### Архитектура WeightAE (авто-выбор кодировщика)

Кодировщик весовых слоёв выбирается автоматически по числу слоёв в модели:

| Число слоёв | Архитектура |
|---|---|
| 1–3 | MLP (полносвязная сеть) |
| 4–8 | CNN (1D дилатированные свёртки) |
| 9–24 | LSTM (двунаправленный, 2 слоя) |
| 25+ | Transformer (само-внимание, 4 головы) |

## Как устроен корпус

Для каждого «проекта» обучается эталонная модель, затем порождаются кандидаты: 8 легитимных
обновлений (дообучение, обучение заново, перевод весов в fp16, обновления зависимостей, дрейф данных)
и по 3 нарушения каждого из 8 классов угроз. Атаки проводятся на самом деле: модель дообучается на
отравленных данных, веса искажаются. Неудавшаяся атака в корпус не попадает. Разбиение на
обучение/валидацию/тест — по проектам. Готовый корпус: `corpus/corpus500_v2.pt` (этим корпусом обучена
продакшн-модель `models/detector.pt`; подробности и честные ограничения — в `docs/methodology.md`).

## Командная строка (для конвейера сборки и поставки)

    python -m integrityguard corpus --projects 500 --out corpus.pt
    python -m integrityguard train --corpus corpus.pt --out run
    python -m integrityguard export --out packages --projects 2        # корпус в виде каталогов пакетов
    python -m integrityguard baseline --package <эталон> --control control.npz
    python -m integrityguard check --package <кандидат> --strict       # 0 допуск, 1 блокировка, 2 на проверку
    python -m integrityguard monitor --package <развёрнутый пакет>     # контроль в эксплуатации
    .venv\\Scripts\\python.exe -m pip install pytest
    .venv\\Scripts\\python.exe -m pytest tests

Каждая проверка добавляет строку JSON в `registry/events.jsonl` — источник событий для SIEM/SOC.

## Формат пакета

    manifest.json   имя, версия, зависимости (имя, версия, sha256, источник, requires, размер)
    manifest.sig    подпись выпуска (HMAC-SHA256 по всем файлам)
    model.pt        веса (state_dict)
    src/*.py        собственные модули
    vendor/<имя>/   код зависимостей (необязательно)

## Ограничения

- Корпус синтетический: небольшие полносвязные сети на модельных задачах и синтетические графы
  зависимостей. На реальных пакетах и моделях показатели не измерялись.
- Поведенческий и параметрический анализ поддерживает модели вида Linear+ReLU, сохранённые как
  state_dict. Для других архитектур нужно дописать функцию прямого прохода.
- Состязательные входы, извлечение модели и нарушение доступности (угрозы 4, 7, 8) — угрозы времени
  выполнения, проверкой артефактов не выявляются напрямую; детектор выявляет косвенные признаки.
- Подпись — симметричный HMAC, это упрощение для прототипа.
- Модель, сохранённая небезопасным pickle, блокируется правилом политики без загрузки файла.
- Детектор надёжно отличает норму от нарушения (бинарный F1/AUC = 1,000), но внутри нарушений три класса —
  «внедрение триггера» (backdoor), «отравление обучающих данных» (poison) и «подмена меток» (label_flip) —
  заметно путаются между собой (macro-F1 по 9 классам ≈ 0,69). Увеличение корпуса и числа эпох обучения
  эту путаницу не снимает (проверено — см. `docs/methodology.md`): все три атаки искажают сам процесс
  обучения модели, а детектор анализирует только результат (веса, граф, поведение), поэтому их финальные
  отпечатки статистически похожи. Для надёжного различения нужен контроль происхождения обучающих данных,
  а не анализ готового артефакта.

## Самопроверка

- `tools/diagnose.py` — проверяет окружение, детектор и создание демо-пакетов; результат в `data/diagnose.log`.
- `tools/selftest_gui.py` — сквозной прогон интерфейса без показа окна (автоподготовка, папка входящих, мониторинг);
  снимки всех страниц и журнал сохраняются в `data/selftest/`.

Запуск: `.venv\Scripts\python.exe tools\selftest_gui.py`.

Для проверки готового дистрибутива запустите тот же сценарий из каталога проекта:

```powershell
$env:INTEGRITYGUARD_SELFTEST_OUT = Join-Path (Get-Location) 'outputs\packaged-gui-run'
$result = Start-Process -FilePath '.\dist\IntegrityGuard\IntegrityGuard.exe' -ArgumentList '--selftest-gui' -Wait -PassThru -WindowStyle Hidden
$result.ExitCode
```

Проверка использует временный каталог данных и модель из дистрибутива. В каталоге результатов сохраняются журнал, снимки страниц и PDF по проверенному пакету. Код 0 означает, что все проверки сценария прошли.

## Кодировка

Все текстовые файлы программы (исходный код, журнал событий, отчёты, манифесты, настройки) читаются и пишутся в UTF-8;
файлы с меткой BOM, сохранённые Блокнотом Windows, тоже принимаются.

## Полнота обнаружения — отдельная функция

Расчёт полноты (Recall) вынесен в модуль `integrityguard/recall.py` и на страницу «Полнота обнаружения»:
по классам угроз, по уровням целостности и по методам. Источники — тестовая выборка детектора (`metrics.json`)
и демо-набор пакетов (кнопка «Рассчитать полноту на демо-наборе»; результат сохраняется в `data/recall.json`,
в журнал событий такие проверки не пишутся).
